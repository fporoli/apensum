# Domain terms, approvals and flows

Project time and work time, the workflow engine, configurable workflows, static data, Free Flows and flow types, Auslöser.\
Moved from CLAUDE.md as it was; CLAUDE.md keeps the rules that apply everywhere and points here.

- Domain terms: **project time** (`project_times`, hours booked against projects) is separate from **work time** (`work_times`, check-in/check-out attendance) and from **balances** (vacation/overtime, `balances.service.ts`).\
  Approval flows (timesheets, expense reports, absences, timesheet reopen) go through `workflows.service.ts` and create notifications (`notifications.service.ts`, which persists rows and pushes over the WS gateway at `/ws/notifications`).\
  The Workflow page (`Approvals.tsx`, `GET workflows/assigned-to-me?scope=assigned|mine&status=pending|approved|rejected|all&orgId=`) shows what the caller decides and, for everyone (097, `nav.approvals:see:own`), their own requests and where they stand; only open items assigned to the caller can be decided.\
  It lives only inside the Flows page now, as the card of one workflow item (`embedded.onlyId`), which asks for that item alone (`id=`, still within the list asked for).\
  A workflow has steps (`workflow_definitions.steps`: `assignTo` `manager` or `permission:<object>` = everyone holding it with edit on all, optional `doneKey`, `actionKey`, `rejectable`, `inDialog`); approving a step moves it to the next (new assignees, notified), the last one finishes it, and `completeStep` does a step that a module's own page did.\
  Configurable workflows (104, `packages/shared/src/workflowConfig.ts`): a module registers a kind (`ApiPluginWorkflows.kinds`: catalogue of building blocks with their actions, allowed assignees and order rules, the facts its conditions may test, the default) and starts it with `WorkflowsService.start`; whoever holds `section.admin.workflows` edit (113: the owner through `OWNER_PERMISSIONS`, and a role the owner gives it to; it decides who sees whose flows) arranges the blocks on Admin settings -> Workflows (`WorkflowSettings.tsx`: one foldable card per kind or flow type, folded by default and remembered for the session, with "Änderungen verwerfen" back to what is saved; switching a step's block keeps its template, fields and assignee aside and brings them back when switching back; the designer `WorkflowDesigner.tsx`, one card per step with blocks, assignee lists, reject, condition rows, labels, and a JSON tab, both editing the same text; a condition the rows can't show is JSON in place with an example to copy; `workflow-configs.controller.ts`, `workflow_definitions.config`, null = default; admins read it): steps with `do` (exactly one block, `one-block`; a list only so the format stays; a block with `fieldsOptional`, the flows' review, may ask fields too), `assignTo` (`manager`, `permission:<object>` as the block allows = every active member holding `<object>:edit:all`, the designer shows who that is today, `department:<id>`), `when` (conditions on facts, skipped otherwise, never on the first step), `reject` (`none`, `back` = to the person to change and submit again), `label`.\
  `assignTo` names departments and teams by their code (105, `departments.code`/`teams.code`, unique per organization, made from the name when not given, the seed sets Acme's; `cleanUnitCode`); changing a code rewrites the stored configurations (`renameUnit`), deleting one a configuration names is refused (`department-in-workflow`, `team-in-workflow`).\
  Absence requests are the kind `absences.request` (`ABSENCE_CATALOGUE` in `absences.controller.ts`: block `review`, a decision, rejecting `end` = final; facts `type`, `days` (calendar, a half day 0.5), `unpaid`, `probation`, `requester.department`, `requester.management`; default the manager); types without approval (sickness, accident) have no workflow. Records become approved only when the last approval is done (`onFinished`), absences and expense reports alike.\
  A kind may have variants (`WorkflowKind.variants`, one definition `<name>:<variant>` each, none stored = no workflow), its catalogue per organization (`catalogueFor`, e.g. facts from form fields) and `onFinished`.\
  `validateWorkflowConfig` runs in the browser and the API; each workflow keeps the steps it started with (`workflows.steps`; older ones read their definition's); the submitter never decides their own submission (steps whose blocks are `decides`, also not through `nav.approvals:edit:all`: `own-submission`; nobody else = HR, then owners), work steps they may do; a manager's review without a manager is approved at once; a module's own page finishes a block with `completeBlock` (the step's last block moves it on).\
  Each workflow row holds its organization (`workflows.organization_id`, 107, from its definition); there are no per-table organization resolvers any more.\
  A change of one's own personal data is a flow (kind `basicdata.change`, `basicdata.controller.ts`, source table `basicdata`, the person's user id; facts `fields` and `sections`; default one step, HR = `section.basicdata.personalien` edit on everyone, rejecting ends it): My Data's "Request a correction" / "Submit" starts it, the last approval applies the change in that organization (`onFinished`, `resolveRequest`), rejecting keeps the data; HR reviews it on the Flows page in its dialog (`BasicDataChangeReview.tsx`, old against new, by the sections the reviewer sees; a core kind the web lists with the plugins', `coreWorkflowKinds.tsx`); the old review queue on My Data keeps only requests from before.\
  Flows don't stay put (`workflow-dues.service.ts`, every 10 minutes, off with `REQUEST_ALERTS=off`): a step whose assignees are away (an approved whole-day absence today, Zurich) goes to their deputies as well (`organization_memberships.deputy_user_id`, 117, set by the person or HR on the employment panel, `PUT .../users/:userId/deputy`; on a step one does for all only when nobody of it is there, on an `each` step the deputy takes the absent one's place; never the submitter of a decision); a step with `remindDays` reminds its assignees after that many working days (Monday to Friday from the step's start, holidays not left out), one with `escalateDays` then goes to their managers today as well, else to HR (`section.people.employment:edit:all`), the assignees keeping it (not on `each` steps); bell and mail (the step's name only), each once per step (`workflow_data.due`), each in the history (`approvals.event.deputy`/`reminded`/`escalated`); set per step in the Flow-Designer ("If it waits"); running flows keep the steps they started with.\
  The Flows page's "Done" (`workflows/assigned-to-me?status=all`) holds one's queue's finished items and recalls what one did a step of (an entry `by` the caller in `workflow_data.history`, not the submission) in the last `WORKFLOW_RECALL_DAYS` days (default 5), also while it waits with someone else (`assigned_to_me: false`, read-only, `flowRows.ts`); flows of an own type stay listed by their request.\
  Every tab shows the newest 200 of each source (`limit`; workflow items by step start, `flows` by last activity, box `done` = the inbox's resolved and the archived), a line above the list (it stays while the list scrolls) and below it says so, and "Load all" reads the rest that matches the filters, 1000 at a time (`before`, each row's `cursor`: time in milliseconds and id); a person who decided thousands of flows over the years thus still opens the page at once.\
  The two lists are shown as one (`flowRows.ts` `shownFrom`): while a source has more, nothing older than its oldest loaded row is shown, so the other's older rows do not stand where the next page belongs.\
  The filters go to the API, so they reach every flow, not only the loaded ones (`flowQueries`, `list-filters.ts`): type (`definition` of a built-in kind, `type` of an own one or `free`; the source without such flows is not asked), period (`since`, last activity), status (`state`: open, done, sent back; Mine and Done), who started it (`person`; To do and Done) and a search (`q`: every word, without case or accents, in the subject or the starter's name or e-mail).\
  Side by side, list and flow each scroll on their own below the app bar, so a flow chosen far down the list is in view at once.\
  Each workflow keeps its history in `workflow_data.history` (`{key, by, at, note}`, `key` a text key: the core's submitted/decision, a plugin's own steps; `recordEvent` adds one); rows from before have it derived from their timestamps, without who decided.\
  Admin-editable dropdown vocabularies live in `static_data`.\
  Each list says what it is for (`static_data.description`, 112, a text per language, `cleanDescription`/`listDescription`; the core's lists get theirs from 112, a plugin's from its changelog; an organization's copy shows the one it copies until it has its own); Admin settings hides a list for all organizations that the organization has its own copy of while "Only my organization" is on (the default).\
  A list maps each key to a label, or to properties with the labels in `translation`; which properties is static data too: the global list `static_data`/`properties` (101) maps `<entity>.<list>.<property>` to `{type: checkbox | radio | select | text, default, list, pattern, sort}` (radio = one value of the list, 102; a list of labels that gets properties keeps them as English translations, `keepLabels`) and describes its own fields, the core's and the plugins' come from migrations, an organization adds its own in its copy (the global ones win); Admin settings shows a control per property (`propertiesOf` in `packages/shared/src/staticData.ts`), never a special case per list; read labels with `staticValueLabel`.\
  Rows for all organizations (`organization_id` NULL) are the defaults: they come from migrations, and operators add to them on Super Admin → Default lists (`operator-static-data.controller.ts`, rules in `static-data-defaults.ts`: add values and lists, change translations, change or remove only what operators added, `static_data.operator_keys` 103; a migration's values and a list's name stay; audited in the Admin organization); an org copies one (Admin settings, the copy icon) and edits its copy, which then replaces it for that org.\
  Absence types (`absences`/`absence_type`) map each key to attributes instead of a label (labels are in `translation`): `{"approval": false}` (set for sickness and accident in the global row, 047) records the absence as approved and notifies the manager instead of asking.\
  `{"unpaid": true}` (the global `unpaid_leave`, 096; Admin settings → static data, "unpaid") marks unpaid leave: the payroll export's unpaid hours (sick leave = `sickness` + `accident`), and each full 30 days of it in a year cut a twelfth of that year's vacation entitlement (Art. 329b para. 1 CO, `unpaidLeaveCut` in `vacation.ts`; HR's override replaces the result).\
  The code keeps no list of types; new orgs inherit the global row (since 090 with maternity and paternity leave).\
  "Basic data" (`basicdata.*`) is personal data with an HR change-request/approval history.
- Free Flows and own types (module `flows`, `flows.controller.ts`, `flows.service.ts`, `FlowDetail.tsx`, tables 052, renamed in 110): Free Flows to the line manager or a department, with a message thread (`flow_messages`, kind `message` or `event`).\
  Handlers are worked out per call, never stored: the requester's manager in force, or the department's members in force and its leader, plus `nav.flows:edit:all` (nobody by default since 092).\
  Any handler takes, answers, sets the status, archives; the requester answers and resolves/reopens.\
  Every change notifies the other side (`source_table = 'flows'`, the bell opens the thread).\
  A request type may have its own workflow (106, `flow-steps.ts`, kind `flows.flow`, one per type on Admin settings -> Workflows): blocks `review` (approve or send back), `task` (done) and `form` (the step's own fields, `WorkflowStepConfig.fields`: text, number, date, checkbox; `stepFieldValues` checks the answers in the browser and the API, kept per person in `workflow_data.inputs` and shown with sums in the thread; `privateAnswers` = for the requester only: others see that someone answered, not what (`visibleThread`), a mail step sends them to the requester alone, and the Workflow page never returns `inputs`) and `mail` (automatic: sent the moment the workflow gets there, alone in its step, `WorkflowStepConfig.message` subject and text per language, optionally the form answers with sums, `workflow-mail.ts`; a confidential request's mail names neither its subject nor the answers; best effort), assignees manager, `requester` (the mail's only), `department:<code>`, `team:<code>`, `person:<user id>` (an active member) or a permission, a unit or permission each on their own (`each`: the step waits until every assignee did it, one who sends it back sends it back for all), facts `urgent`, `type`, `requester.department` (code), `requester.management` and the request's fields (`field.<key>`).\
  A step may write an e-mail (block `compose`, "E-Mail schreiben", `flow-compose.ts`): its template is the step's `message` (subject and text per language, written in the designer) and `mailTo` says whom it goes to (`about` = the person the flow is about, the default; `requester`; `aboutManager` = that person's manager today; `choose` = nobody set, the writer picks).\
  The template is optional: without one (or with subject and text blank in every language) the window opens empty, a plain "write an e-mail to someone" step.\
  Whoever does the step opens the e-mail (`GET flows/:id/compose`: the template filled in the recipient's language, else the sender's), may change it and the recipients (active members only, at most 20), and sends it (`POST flows/:id/compose`, `{ userIds, subject, message }`): from the app's address with Reply-To the sender, without a link (the recipient may not see the flow) and without a footer of its own (the text ends with the sender's greeting, `{{sender}}` in the templates), each in their own mail.\
  The thread says that the e-mail went out and to how many, never what it said (the audit log `flow.compose-mail` the count only); `workflow_data.composed` marks the step, and the step is done (its button, `flow.done`) only afterwards (`mail-not-sent`).\
  The template's placeholders keep their English names in every language: `{{name}}` and `{{firstName}}` (the person it is about), `{{date}}` and `{{years}}` (a task's values, `flows.task_data`, the date the Swiss way), `{{subject}}` (left empty on a confidential flow) and `{{sender}}`; one without a value, or unknown, stays as typed (`fillPlaceholders` in `workflowConfig.ts`); the designer lists them.\
  A step that goes to several people (a department, team or permission, not `each`) is taken over first (`takeOver` in the catalogue, compiled onto the step; workflows started before keep their steps): `POST workflows/:id/take` narrows its assignees to the caller (`workflow_data.taken` keeps whom it had), the others are notified and the thread says so; `{ release: true }` gives it back to them; until then its buttons are refused (`take-first`), except for an approvals grant reaching everyone.\
  The flow's whole "Übernehmen" is not offered for a flow with set steps: they are taken step by step.\
  Each flow knows whom it is about (121, `flows.about_user_id`: the requester for one someone starts, the person for a task).\
  A request type may have its own fields (form `flow.<type>`, `flowTypeForm`/`formById` in `fields.ts`, designed on the Flows page in design mode by choosing the type): shown and checked after every request's (`flow`), stored with them in `flows.custom`.\
  The seed gives Acme the example: department Frontdesk (`frontdesk`), the type `material` ("Materialbestellung") with fields article, quantity, amount, and its workflow (manager, finance above CHF 500, Frontdesk orders, hands over).\
  Such a request has `target_kind = 'workflow'` (the requester picks no target), its handlers are whoever its steps went or go to (`workflowParticipants`), its status follows the steps (open, in progress, resolved when the last is done), the thread shows each step (`data.workflow`), the requester submits it again after it was sent back (`resubmit`) or withdraws it (`withdraw`); it also shows on the Workflow page ("Request", Open).\
  Each request has a type (static_data `flows`/`flow_type`, global row in 069: service, support, other; `{"sort": n}` orders them), an `urgent` flag and an optional http(s) `link_url`; validation is `packages/shared/src/flows.ts` plus `validateFlowDetails`, and requester or handler change them via `POST flows/:id/details`.\
  Messages carry attachments (054): files go through `DocumentsService` (`documents` rows naming their message: `source_table = 'flow_messages'`, 115), uploaded multipart in `files` on create/reply, downloaded via `flows/:id/attachments/:documentId` with the request's access check; the web composer takes the paperclip, drag-and-drop and pasted screenshots (`attachments.tsx`).\
  A request may have a due date (088, `due_date`, `cleanDueDate`; create, details): once it has passed while the request is open, `FlowsService` (every 10 minutes, `REQUEST_ALERTS=off` disables it) mails and notifies the assignee, else the handlers, an urgent one both (`overdueRecipients`: so someone can take it over), once per due date (`overdue_alerted_at`, reset when the date changes).\
  An urgent request to the manager or a department that nobody has taken for 4 hours (open, no assignee; `URGENT_UNTAKEN_MS`) reminds everyone who handles it, once (120, `urgent_alerted_at`; `alertUrgentUntaken`, the same runner); a confidential one names neither subject nor text.\
  The handlers of a department request are whoever is in it today and its leader, while they are still there (not past their exit).\
  Modules and plugins open tasks (`FlowsService.openTask`/`closeTasks`, in the plugin contract): no requester, `source` (shown as the sender, `modules.<source>`), `source_key` (one per key and organization), `source_section` (the page an "Open in" button shows), to a department unless it says otherwise (`target`, below); a resolved or archived task is never reopened, `closeTasks` resolves a source's open tasks not kept (only those under `keyPrefix` when given), and `flows-off` when the module is off.\
  A task may name the person it is about (`aboutUserId`, a member: the "Open in" button opens its page with `?user=<id>`), values for its steps' e-mails (`data`, `flows.task_data`) and a flow type (`flowType`): when the type has its own steps the task goes through them instead of to the department (122 lets a task without requester have `target_kind = 'workflow'`; the workflow starts without a submitter), and an open task of that kind nobody took yet switches to them at the next sync.\
  The first step of a flow type is always one that can be sent back (`first-step-decides`), so a type for tasks starts with `reject: back`; a task has nobody to send it back to, and its card offers no "send back".\
  A task without steps goes to a department (`target`, default), to the acting manager of the person it is about (`manager`: `target_kind = 'manager'` without requester, `handlerIds` and the list take the person it is about) or to that person (`person`, `target_kind = 'person'`, 123).\
  Handlers come from `FlowsService.handlerIds`; queries on the requester use `IS DISTINCT FROM` (it may be NULL).\
  A request type with the attribute `{"confidential": true}` (Admin settings → static data, the "Confidential" checkbox; the global type `hr` since 089) makes its requests confidential (`flows.confidential`, set on create and type change), and so does the requester's "Confidential" when sending one (the new-flow dialog; the hint says who sees it); a confidential request stays so whatever type it gets later: only the requester and the handlers see them, `nav.flows:edit:all` does not (`handlesCondition`, `access`), notifications and overdue mails carry neither subject nor text (`noticeSubject`, `overdueMail`: use them for anything sent about a request), "Send by e-mail" returns `flow-confidential`, and the assistant's request tools skip them; it is access control, not encryption.\
  The organization's own fields on requests are the configurable form `flow` (`FLOW_FORM` in `fields.ts`, custom fields only, designed in design mode on the Flows page, `FlowCustomFields.tsx`), stored in `flows.custom` and checked with `customValuesErrors` (shared with the Cases plugin's forms) on create and in `details`.
- **Auslöser** (triggers; EN trigger, FR déclencheur, IT attivatore; `triggers.ts`, `triggers.service.ts`, `flow-triggers.controller.ts`, table `flow_triggers` 123, web `FlowTriggers.tsx`): an organization's rule that opens a flow when an event comes up, `lead_days` ahead.\
  Events come from the core (`CORE_TRIGGERS`: `permitExpires`, from My Data's `residencePermitValidUntil`) and from plugins (`ApiPlugin.triggers`, a `TriggerSource`: its events with labels in four languages, the placeholders they give the e-mail templates, a default lead time or `false` for "as soon as known", the page their link opens, and `due(db, orgId, today, horizons)` returning the occurrences: key, the person it is about, date, due date, values, subject and message per language; e.g. HR-Prozesse's deadlines and exit steps).\
  A trigger has its event, on/off, lead days (0-365), a flow type (its steps take the flow, e.g. "E-Mail schreiben" to the person) or none (a Free Flow to a department, to the manager of the person it is about, or to that person), confidential, and a name (`validateTrigger`).\
  `TriggersService` runs each organization's triggers a minute after the start and every hour (`TRIGGERS=off` turns it off), and when a trigger is saved or `POST flow-triggers/run` is called (HR-Prozesse after an exit date): it opens each occurrence through `openTask` (source `trigger`, key `trigger:<trigger id>:<occurrence key>`, in the language of who gets it first), brings open ones up to date and resolves that trigger's open flows whose occurrence is gone (`closeTasks` with the trigger's key prefix); a disabled or deleted trigger resolves its open flows; one whose event's module is off (or unlicensed) is left alone and shown greyed out; a source that fails leaves its flows as they are.\
  Every run is kept (`flow_trigger_runs`, 124): when, who started it (none: the hourly job), the flows opened, updated and closed, and per trigger its event, counts and an error code (`source-failed`, an `openTask` error), never whom a flow is about; runs that changed nothing are kept two days, the others 90.\
  The Auslöser tab shows them as "Letzte Läufe" (`GET flow-triggers/runs`, `quiet=1` with the quiet ones; only the triggers the caller sees count) with "Jetzt ausführen", and a run that changed something or failed writes one line to the API's log (`TriggersService`: counts and the organization's id).\
  Who: an event about people's data (`TriggerEventDef.sensitive`: the permit, `section.basicdata.personalien`; HR-Prozesse's, `nav.hr`) is seen and set up only by who edits that object for everyone (HR), with or without the Flow-Designer, nobody else (not the owner, not an admin); the others' triggers are changed by `section.admin.workflows` edit and read by admins.\
  The tab "Auslöser" of Admin settings -> Flow-Designer and HR-Prozesse -> Einstellungen show the same panel (in the web plugin contract), each with the events its reader may see.\
  Vorlagen (`POST flow-triggers/templates`, listed by `GET flow-triggers` as `templates`): the core's for a permit expiring (`packages/shared/src/triggerTemplates.ts`), a plugin's for its own events (`TriggerSource.templates`, offered while its module is on: HR-Prozesse's for an anniversary, the end of probation and an exit), each a flow type with a step "E-Mail schreiben" to the person (a text in four languages, Sie in German) to the chosen department (by its code), and for the permit a second one, the task "Neue Bewilligung erfassen" (`followUp`: same department, may go back to the e-mail, reminded after ten working days), and the event's trigger (an existing one goes through the new type); for whoever sets up the event, since the type is fixed by the template.\
  The core's own reminder of a permit ending (`WorkflowDuesService`) stays silent in an organization with an enabled `permitExpires` trigger (`permitTriggered`; the plugin hook `permitReminders` is deprecated).\
  The HR plugin's former "Fristen als Flows" settings (`settings.hr.tasks`, `permitLeadDays`) became triggers (HR changelog 009): one per kind plus the permit's, to the same department with the same lead times and flow types, confidential; the flows they had opened kept going under their new keys (`hr:<kind>:...` to `trigger:<id>:<kind>:...`, resolved ones too, so none is opened again), and the two settings were removed.
