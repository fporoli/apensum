# Access: sign-in, permissions, roles

Sessions and single sign-on, two-step login, invitations, registration, operators, monitoring, backups, the permission catalogue and the roles.\
Moved from CLAUDE.md as it was; CLAUDE.md keeps the rules that apply everywhere and points here.

- Auth: global `JwtAuthGuard` (`jwt.guard.ts`) accepts local HS256 tokens (`API_JWT_SECRET`) only.\
  Single sign-on (docs/OPERATIONS.md "Single sign-on"): one provider per instance, `SSO_PROVIDER` `none` (default) / `dex` / `keycloak` (Compose profiles; `remote.sh` writes Dex's config, connectors from the secret `DEX_CONNECTORS`, else Dex's test login); the web app (`auth.ts`, `oidc-client-ts`, code flow + PKCE) asks public `GET auth/sso` and hands the ID token once to `POST auth/sso/exchange`, which checks it (`verifySsoIdToken`: JWKS, issuer, audience, at most 10 minutes old) and returns a local session; an SSO token is never a session.\
  Use `@Public()` to opt a route out.\
  Password logins count failures only (`password-reset.ts`: 10 per account and address, 50 per address, 200 per account from anywhere, per hour, then `too-many-attempts`), registrations 5 per address and hour; in memory, per API process.\
  CORS allows the web app (`APP_BASE_URL`), the website (`CONTACT_SITE_ORIGINS`) and `CORS_EXTRA_ORIGINS` (`cors.ts`; without `APP_BASE_URL` every origin).\
  The edge Caddy sends the app's security headers (`infra/caddy/edge/sites/worktime3.caddy.tpl`: a strict CSP, no framing, HSTS): never add inline scripts, and a new origin the app talks to goes into its CSP.\
  Frames and objects allow only `blob:` (besides the sign-on host): the Documents page previews a PDF from a blob the app made, and the browser's PDF viewer counts as an object.\
  `sql.raw` gets only text written in the code (`test/api/sql-raw.test.ts`).\
  A session token carries its password's stamp (`pv`, `session-state.ts` `mintSessionToken`); the guard and the WebSocket check that the account is active and the password the same (`sessionHolds`, cached 30 s, `forgetSessions` after a reset): changing the password or deactivating the account ends every other session; tokens without `pv` (older) hold until they expire. Mint session tokens only with `mintSessionToken`.\
  The web app signs out on a 401 to a request that carried the token and the login page says why (`sessionWatch.ts`).\
  Forgot password (`password-reset.ts`): `auth/reset` mails a signed link (30 min, bound to the current password hash, so one use; key from `purposeKey`), `#/reset/<token>` (`ResetPassword.tsx`, no login) sends it to `auth/reset/confirm`.\
  No public endpoint may set a password from an e-mail address alone.\
  Two-step login (099, `totp.ts` pure RFC 6238 + recovery codes, `two-factor.ts`, `two-factor.controller.ts`, web `TwoFactor.tsx`; password accounts only, SSO keeps its identity provider's): optional for everyone in Settings; an organization's rule `organizations.settings.twoFactor` (`off` / `privileged` = admins and HR, `isPrivileged` in `packages/shared/src/twoFactor.ts` / `all`, Organization settings -> Security, `nav.orgSettings` edit, audited) and the Admin organization always require it.\
  An account spans organizations, so it applies at login (`issueSession`): any membership requiring it and not set up gives a 30-minute token with `scope: 'two-factor-setup'` that reaches only `@TwoFactorSetup()` handlers (`jwt.guard.ts`) and no notifications; when it is on, the password only earns a 5-minute challenge (bound to the password hash) for `auth/login/two-factor`, and accepting an invitation with such an account answers `signInRequired`.\
  A code works once (`last_step`), a recovery code is removed when used, 10 attempts per account and hour; no organization turns it off or resets it (the operator CLI's `twofactor reset` does, for a lost phone).\
  `TWO_FACTOR=off` (GitHub Environment variable, set on demo and test, never on prod or preprod; `twoFactorOff`) turns it off on an instance: nothing is required or asked, operators included, and Settings says so.\
  Secrets are encrypted with `purposeKey('two-factor-secret')`: changing `API_JWT_SECRET` leaves everyone with their recovery codes only.\
  Accounts span organizations, so no organization's rights change one or act as one.\
  `PATCH users/:id` is one's own only, and there is no impersonation: nobody gets a token of someone else's account.\
  An invitation's token is known to the inviter: accepting with an existing account takes that account's password and never sets one (only a new account, or one without any login that belongs to the inviting organization alone).\
  The import never attaches an existing account, it invites it; there is no restore (recovery is from database dumps, the documents volume and `DOCUMENTS_KEY`).\
  The employee import writes a person's details into the organization's section (`basicdata.orgs.<orgId>.personalien`) and renames only someone who belongs to it alone; HR's form keeps the personnel number (like the birth date) in the organization's own keys (`orgOwnedKeys`); `payrollPersonalien` and `scopeToOrg` read both, in the same order.\
  SSO picks the account from the token's verified e-mail, never from the body.\
  Any id from a request (user, membership, team lead) is checked against the organization before it is stored or grants access.\
  Membership settings hold the person's calendar-feed token: return, audit or take them only through `membership-settings.ts`.\
  Registration is open: each registration gets its own workspace as owner, admin and HR (`registrationRoleIds`); nobody becomes operator by registering, the first account included: `operators grant` of the operator CLI (or an operator on the Superusers page) does it.\
  Every registration is told to the operators (`registration-notice.ts`): a mail in each one's language and a notification in the Admin organization (`organizations`, opening Super Admin → Licenses), best effort.\
  With `NTFY_TOPIC_URL` (a secret, prod) the operator's phone gets a short hint through ntfy (`operator-push.ts`, JSON publishing, 5 s, never fails a request) on a website contact message (its topic only), a registration and a monitor finding; a push never carries personal data (the public server is not in Switzerland): use it for the chatbot's hand-over too.\
  Monitoring (docs/OPERATIONS.md "Monitoring"): outside `.github/workflows/monitor.yml` (`MONITOR_TARGETS`, two failures in a row before a mail, recovery and certificates, mail via prod's SMTP to its `OPERATOR_EMAIL`; GitHub thins the schedule out, so an uptime service checks public `GET health/db`, 200 or 503 only); inside `monitor.service.ts` (hourly, disk and mail relay, once a day each, `MONITOR=off`), notifications `operator_monitor` opening Super Admin → Instance.\
  Backups (docs/OPERATIONS.md "Backups", `.github/workflows/backup.yml`, `infra/vps/backup.sh`): nightly and hourly 04-19 UTC per VPS environment with `BACKUP_S3_ENDPOINT`, database and documents encrypted on the server with the age public key `BACKUP_AGE_RECIPIENT`, moved by the runner to an S3-compatible bucket (MinIO; the server holds no key to it), retention `scripts/backup-retention.mjs`, monthly `verify`, manual `restore` of the whole instance (`RESTORE <env>`); never of one organization.\
  Handlers take `@Req() req: AuthenticatedRequest`.
- Permissions: ids are `<object>:<action>:<scope>` (`nav.balances:see:reports`, `section.basicdata.personalien:edit:all`), catalogued in `packages/shared/src/permissions.ts` and in Liquibase (035-037), held via `membership_roles` -> `role_permissions`.\
  Global roles (`organization_id` NULL) carry the defaults, changed only by migrations; an org customizes a role by getting its own copy (same name; memberships are moved onto it, "reset" moves them back), or creates its own roles.\
  Admin settings -> Roles & permissions (`roles.controller.ts`) manages the organization's.\
  `owner` is granted, invited and revoked by owners only (`canManageRole`; on accept `invitationNeedsOwner`), and the last one stays (`last-owner`).\
  `roles.admin_user_ids` is no longer read.\
  The instance's operators (superusers, formerly `users.is_superdeveloper`) are the active members of the fixed Admin organization (`OPERATOR_ORG_ID`, `packages/shared/src/operator.ts`, 098; `isOperator` in `access.ts`): AI limits, product news, licenses, superusers; nothing inside any other organization, and never add a check on it for anything else.\
  In the Admin organization `permissionIdsOf` gives its members `nav.operator:edit:all` and nothing else, whatever any role says (not in the catalogue, never grantable), so its navbar shows only the Super Admin pages (`SuperAdmin.tsx`: Instance, Licenses, AI limits, Product news, Default lists, Superusers; API `operator/*` in `operator.controller.ts`; Home shows `SuperAdminHome` there, and App.tsx draws a red frame) and nobody manages members, roles or invitations in it.\
  Members come and go only through the SQL functions `operator_grant`/`operator_revoke` (the first grant creates the organization): the operator CLI's `operators`, the Superusers page (existing accounts only, the last one stays, audited in the Admin organization), and on every VPS deploy and reset (the public demo included) `operators ensure` (`OPERATOR_EMAIL`, default `admin@admin.local`, password from the secret `OPERATOR_PASSWORD`, passed by environment only: run logs are public); it is never listed or licensed as a customer.\
  `edit` implies `see`; a section also requires its parent navbar entry (My data for own data, Users for others').\
  Four roles, three rules: owner decides who is who, admin runs the system, HR runs the people side, a manager sees the line HR gave them.\
  1. Only an owner gives or takes owner, admin, hr, billing_admin and an organization's own roles (`ownerAppoints`, by name); manager, member, guest and developer also an admin (`canManageRole`, `owner-required`).\
  2. Only an owner changes what a role may do (`OWNER_ONLY_OBJECTS`); that is why rule 1 can go by name.\
  3. Only HR changes departments and reporting lines (`section.people.employment` edit on everyone).\
  `owner` holds exactly `OWNER_PERMISSIONS`, never its rows; `admin` always keeps Admin settings.\
  A new object about other people's data is granted to HR and, by reporting line, to managers, never to admin, developer or owner; nor may anything an admin edits route such data to them.\
  The audit log says that something happened, never what it says (admins read it): no notes, reasons, file names or values of people's data in its metadata.\
  An invitation's link goes only to the invited address by mail, never into a response, log or history (`invitation-mail-failed` when it can't be sent).\
  An organization without an owner gets one from the operator's CLI only (`apps/api/src/cli/operator.ts`, `owner list|set`; `license list|grant|revoke`; `operators list|grant|revoke`, history in `versions`).\
  People's data: `canSeeUserData` = self, anyone above them in the reporting line (the manager, that manager's manager, ... `isAboveInReportingLine`, read-only), or a grant covering them; `listableUserIds` adds the whole line below (`reportingLineUserIds`).\
  Editing, approving and reopening stay with the direct manager (`isManagerOf`, `canEditUserData`); `time-record-people` flags each person `editable` and the time pages are read-only for the others; admin-only overrides use `canEditBeyondOwn` (ignores everyone's `:edit:own`).\
  New navbar entries/sections need a registry entry, catalogue rows and default grants (a new `NNN-permission-*.sql` changelog); the catalogue test checks those match the registry.
- Roles are per organization.\
  A membership can hold several roles (`membership_roles`).\
  "Manager of X" is the manager of X's employee assignment in force (`employee_assignments`: dated department, function and manager per person, 050), read through `membershipManagerId` / `directReportUserIds`, never stored elsewhere.\
  The manager who acts for X today (`actingManagerId`, for a whole organization `actingManagers`) is that manager, or, when they have left the organization (no longer an active member or past their exit) and HR has not named a successor yet, the next one up X's line who is still there (at most 10 levels); nobody when the whole line above has left (HR and admin reach such requests anyway).\
  Requests are routed and decided by the acting manager: `isManagerOf` (approving, reopening, correcting), the steps that go to the manager, Free Flows to the manager (handlers, list and badge), submitting absences and timesheets; `membershipManagerId` stays the assignment's own answer (the line as recorded, its loops checked when HR sets a manager).\
  Approvals route to that specific manager, not to any org manager; pending manager requests move to the acting manager when it changes (`WorkflowsService.rerouteToCurrentManagers`, run on writes, on the Approvals inbox, before a decision and every 10 minutes): from an earlier manager, from one who has left, and from one above who stood in once a successor is named; a request with someone else (a deputy beside the manager, another step) stays.\
  Departments (Users page, HR, `departments`) have a default leader, which is only offered as manager.\
  Employment (start date `organization_memberships.start_date` plus assignments, `employment.controller.ts`, `EmploymentPanel`) is `section.people.employment`: HR edits it (051, 092), and with it the departments (Users page).\
  The last working day is set there too (`PUT organizations/:orgId/users/:userId/exit-date`, `{ lastDay }`): `organization_memberships.exit_at` holds the start of the next day in the person's zone (`lastWorkingDay` reads it back); balances stop counting from it, the vacation entitlement is prorated to it and the directory drops the person after it.
